# 工单与硬验收规范

网页版 GPT 必须按照本规范输出工单。目标是让本地 Codex 能够直接执行，同时能发现并修正 GitHub 规划与本机现实之间的脱节。

## 工单头

必须包含以下字段。

```text
工单名称
目标仓库
基线 commit
目标
为什么现在做
允许修改的范围
明确不做的事项
本地执行前必须核对的前提
```

## 当前判断

先用不超过五条说明以下内容。

- 当前最重要的问题
- 决定该判断的 GitHub 证据
- 最强替代解释
- 哪项本机事实可能推翻当前判断
- 为什么这张工单比其他候选工作优先

不得只给功能清单。

## 修改清单

使用表格逐项写明。

| 文件或目录 | 当前问题 | 要做的修改 | 不允许改变的内容 | 完成证据 |
|---|---|---|---|---|

GitHub 中不存在的本机路径必须标为本地核对项，不能写成已确认存在。

## 执行顺序

每一步必须包含以下内容。

1. 输入
2. 具体动作
3. 产生的文件或状态
4. 失败时停止条件
5. 进入下一步的条件

不能使用进一步优化、适当完善、视情况调整等无法判定的动作。

## 硬验收矩阵

每条验收必须二元可判定。

| 编号 | 验收对象 | 通过条件 | 验证命令或证据 | 失败后动作 | 验收位置 |
|---|---|---|---|---|---|

验收位置只能是以下三类之一。

- GitHub
- 本机
- 多节点

## 必须覆盖的验收类型

### 定位不跑偏

- 文献解读、科研思维培养和个人课题推进保持三层递进
- 读文献不能退化为摘要复述
- 证据边界不能取代科研逻辑讲解
- 基础版方法仍在读文献时固定调用

### 科学边界

- 相关性、富集、预测和表达变化没有被升级为因果
- 创作者材料没有被当作科学事实
- 负结果、冲突结果和未知环节没有被隐藏
- 新增方法注明来源、适用条件和不适用条件

### 语料与来源

- 新增材料有稳定来源定位和质量状态
- OCR、ASR 和可靠文本没有混写
- 提取完成没有被描述为深度蒸馏完成
- 排除材料没有进入检索和方法候选

### 中文表达

- 符合中文生信和科研社区习惯
- 不暴露不必要的内部维护术语
- 没有重复套话、无效防御性表达和生硬 AI 句式
- 真实限制仍被保留

### 确定性验证

- Skill 结构检查通过
- 与本次改动直接相关的脚本测试通过
- 失败数量为零
- 若修改方法单元，必须提供边界测试和相邻任务诱饵

### 真实任务回归

- 文献解读必须使用真实论文正文或可核对的一手全文，不得只用摘要代替主 Figure 逻辑验收
- 找课题思路和结果梳理必须包含冲突、阴性或信息不足场景，不能只测顺畅的正结果
- 生成阶段不得读取预期答案、旧评价或其他案例输出
- 评价阶段按核心问题、证据准确、边界与冲突、科研思维、课题推进和中文科研表达逐题二元判断
- 确定性脚本只负责禁用字符、套话和内部术语，不得把固定关键词命中当作内容通过条件
- 所有用户可见输出必须执行终稿自查。任何不符合中文生信和科研社区表达习惯的词、句子或观点均视为失败
- 真实任务回归通过不能自动解除方法单元的 `candidate` 状态，也不能替代尚未完成的边界类型和一手方法学审查

### 本机与同步

- GitHub 快照与本机运行源差异得到说明
- 本机安装入口能读取目标版本
- 需要远端同步时，四节点使用正确 Python 版本完成验证
- 不能把 GitHub 文件存在等同于本机和远端已同步

### 安全与仓库卫生

- 没有原始私有语料、数据库、音视频、密钥和日志进入提交
- 没有混入其他 Skill 或其他项目的改动
- 暂存文件与工单允许范围完全一致
- 提交后远端 commit 与本地 commit 一致

## 验收证据

每个通过结论至少提供一种证据。

- 文件路径和行号
- 命令与退出码
- 测试通过和失败数量
- 文件哈希
- Git commit
- 实际渲染或实际输出

不得只写人工检查通过。

## 回传给本地 Codex 的内容

工单结尾必须单独给出以下区块。

```text
基线 GitHub commit
必须先读的文件
本地必须重新核对的事实
允许本地 Codex 调整的实现路径
不得改变的目标与验收标准
需要用户决策的真正分叉
```

如果没有真正阻断问题，不要向用户提出多余问题。
